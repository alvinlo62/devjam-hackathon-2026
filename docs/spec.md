## 一、專案定位

**一句話**：讓清潔隊班長早上打開系統，今天的案件已經排好路線、標好所需資源。

**不是**：民眾線上預約平台（新北市已有完整線上預約系統，台北市可透過 1999 陳情系統辦理，此非創新點）。

**是**：調度端的決策輔助系統，把目前仰賴人工經驗的排程與資格判定自動化。

| 角色 | 定位 | 本次是否開發 |
|---|---|---|
| **清潔隊班長** | ✅ **主要使用者**，Demo 主角 | 是，主力 |
| 民眾 | 案件來源 | 是，簡化版 |

## 三、核心功能範圍

### 3.1 民眾端 ✅

**介面型態**：訊息流（對話外觀），agent 的每則訊息由結構化區塊組成。

**關鍵約束**：✅ 輸入以**點擊為主**。自由輸入框可存在，但僅供補充說明，不得成為流程必要環節。

訊息區塊型態：

| type | 用途 |
|---|---|
| `text` | 說明文字 |
| `choices` | 選項按鈕組（agent 追問用） |
| `upload` | 照片上傳區 |
| `result` | 判定結果卡 |

**明確不做** ✅：案件狀態查詢頁、案件取消、歷史記錄、多輪上下文持久化。
對話生命週期＝送一件案子，送完即結束。

### 3.2 政府端（班長儀表板）✅

**主畫面** 🔵：**清單為主 + 靜態地圖縮圖**

- 主體：依序排列的任務卡片（第 1 站、第 2 站…）
- 側欄：Maps Static API 產生的路線縮圖（`<img>` 標籤，不引入 JS SDK）
- 理由：清單資訊密度高，地圖在三分鐘 Demo 中無人互動；靜態圖以 20 分鐘成本換取八成視覺效果

**必備面板** ✅：**Agent 決策軌跡**（見 §5.3，這是 Demo 主要爆點）

## 四、排程設計

### 4.1 問題規模 🔵

✅ **採用：單車路線排序（TSP）+ 行政區分組**

**不做**：多車分派（VRP）、時間窗限制（VRPTW）。

作法：案件先依行政區分組（查表，非演算法），每組內做最近鄰居排序。畫面呈現為「今日三班次：信義區 12 件、大安區 9 件、松山區 8 件」。

**依據**：現實中清潔隊按轄區分隊，一車不跨區，故分區比 VRP 更貼近實務。

> ⚠️ **簡報用語規範**：不得宣稱「車輛路徑最佳化」。正確說法為「單一班次的路線排序與載重檢查」。誇大會被懂物流的評審當場拆穿。

### 4.2 載重處理 🔵

只做**檢查**，不做**重分配**。

- 累加體積 → 超過容量閾值 → 標紅色警示
- 顯示「本班次已達 96%，建議移至明日」
- 判斷超載是加法；重新分配才是難題。只做前者。

### 4.3 距離資料 ✅

**抽成可替換介面**：

```python
# services/distance.py
def get_matrix(locations, source="haversine"):
    if source == "google":
        return _from_routes_api(locations)   # 真實路程
    return _haversine_matrix(locations)      # 開發與離線用
```

| 階段 | 使用 | 理由 |
|---|---|---|
| 開發演算法 | Haversine | 毫秒級，可反覆測試，不燒配額 |
| Demo 正式 | Routes API 真實矩陣 | 準確，簡報可述 |
| 現場執行 | 上述矩陣存為 fixture | 避免 900 元素的等待空白 |

`DEMO_MODE` 控制此開關。

**Routes API 實作提醒** ⚠️：
- `X-Goog-FieldMask` 為必填 **header**（非 body），遺漏直接 400
- ComputeRouteMatrix 按元素數計費，30×30 = 900 元素，**務必在 Google Cloud 設每日用量上限**
- 已確認：Routes API 已開通

### 4.4 重新排程觸發 🔵

✅ **採用：計算插入成本，顯示建議，人工接受**

```
新案件進入 → 計算最佳插入位置與成本（插入後總時間 − 原總時間）
          → 顯示「建議插入第 3 站後，+4 分鐘」
          → 班長點擊接受 → 路線更新
```

**不採用**：全自動重排（班長已出車時路線亂變）、純按鈕觸發（少了建議的價值）。

**設計理由**：符合公部門場景——系統輔助決策，不取代決策。

## 五、AI 與程式的職責切分

### 5.1 環節分配 ✅

| # | 環節 | 負責 | 理由 |
|---|---|---|---|
| 1 | 照片 → 物品類型、尺寸、材質 | **Gemini** | 視覺理解無替代方案 |
| 2 | 資格判定 | **`services/`** | 規則含例外與裁量，見 §6 |
| 3 | 屬性標記與資源建議 | **`services/`** | 對應表，非推理 |
| 4 | 路線排序、載重計算 | **`services/`** | 核心，AI 絕不可碰 |
| 5 | 結果敘述 | **Gemini** | 結構化資料轉人話 |

**鐵則**：`services/` 內不得 `import ai`，不得呼叫外部 API，所有函式為純函式。

### 5.2 Agent 的定位 ✅

**Agent ≠ 親自計算，而是自主決定行動序列。**

類比：優秀的調度主管不親自用計算機算距離，他決定該查什麼、查完發現超載後該怎麼辦。模型是主管，`services/` 是計算器。

**Agent 實際做的決策**：

```
新案件進來
├─ 決定：照片資訊是否足夠？不足 → 追問民眾
├─ 決定：呼叫資格查詢
├─ 資格回傳 needs_review
│   └─ 決定：是否先算插入成本供班長參考
├─ 決定：計算插入位置
├─ 插入後超載
│   └─ 決定：不硬塞，改查明日班次是否有餘裕   ← 關鍵決策點
└─ 決定：向班長說明什麼、強調哪一點
```

**「超載 → 於是改查明日」即為 agent 的證據**：非預寫的 if-else，而是模型看到工具回傳結果後自行決定下一步。

### 5.3 Agent 決策軌跡面板 ✅

**這是本專案最重要的 UI 元件。**

```
🔍 分析照片…
   → 辨識：彈簧床墊 × 1，長度 >180cm，不可拆解

📋 查詢收運資格…
   → 符合家戶巨大垃圾範圍

📍 計算插入位置…
   → 最佳位置：第 3 站後，+4 分鐘

⚠️ 檢查載重…
   → 插入後達 103%，超過本班次容量

🔄 改為查詢明日班次…              ← 全場最重要的一行
   → 明日該區餘裕 42%，可容納

✅ 建議：排入明日第 2 站
```

**實作簡化** 🔵：不需 streaming。後端將決策步驟收集為陣列，隨最終結果一併回傳，前端逐行動畫顯示即可，視覺效果相同。

**與民眾端共用渲染邏輯**：兩端都是「把 agent 的每一步渲染成區塊」，單人開發可省下大量時間。

## 六、資格判定規則

### 6.1 三種判定狀態 ✅

```
eligible      → 明確符合（沙發、床墊、電視等清單品項）
ineligible    → 明確不符合（行李箱少於 3 只、石材類、法人申請）
needs_review  → 需清潔隊裁量
```

**`needs_review` 是設計重點**：承認系統不該假裝全自動。畫面上呈現為待審佇列，交班長裁量。此設計貼近實務，對熟悉公部門的評審有加分作用。

### 6.2 已確認的規則（來源：臺北市環保局常見問答）

**收運品項**：廢棄家具（彈簧床墊、床組、手推車、腳踏車、電動腳踏車、微型電動二輪車、電風扇、沙發、桌椅、櫥櫃）、家電（抽油煙機、瓦斯爐、大型飲水機、電視機、電冰箱、洗衣機、冷氣機、立燈、落地燈）、樹枝。

**明確門檻**：
- 廢行李箱 **3 只（含）以上**才算 ← Demo 佐證用
- 服務對象限「一般家庭及住戶」，**排除**住家兼營商業、機構、學校、部隊、法人
- 至少提前**一日**預約
- 多數區要求夜間 **21 時後**排出
- 收運時間週一至週六，**週日不收運**

**裁量條款**（→ `needs_review`）：
「個人自行修繕之**非石材類**廢棄物」，由清潔隊依三項因素判斷：
1. 實際收運數量
2. **是否為裝修業主修繕**
3. **已預約清運案件數量**

### 6.3 裁量條款的系統化 ✅

第 2 項無法查詢（無資料庫記載施工方），**改由 agent 追問民眾**：

```
偵測疑似裝潢廢料
  → agent 追問：「這是您自行拆除的，還是請廠商施工？」
  → 民眾點選
  → 自行拆除 → needs_review（進待審佇列）
  → 請廠商   → ineligible（告知委託合格清除業者管道）
```

第 3 項「已預約案件數量」**正好是本系統算得出來的**，形成閉環：

> 「此件裝潢廢料，今日該區已排 28 件、載重 92%，建議排入明日班次」

### 6.4 為何資格判定不可交給模型

規則的共同特徵是**反直覺的門檻與排除**。模型看到「兩只行李箱」會自然回答「行李箱屬大型廢棄物，可收」——因為訓練資料裡行李箱就是大型廢棄物，**它不會知道有 3 只門檻**。

後果直接：民眾依系統指示擺出兩只行李箱，清潔隊未收，民眾可能因隨意棄置受罰。

> ⚠️ 罰則金額（曾見 1,200–6,000 元之說）**須向環保局確認**後方可寫入簡報。

## 七、資源屬性設計

### 7.1 採用屬性標記，非工具清單 🔵

**不做**：「彈簧床墊 → 2 人 + 推車」這類無來源依據的主張。

**改做**：標記物品**客觀屬性**，再由屬性推導建議。

```
彈簧床墊 × 1
  重量級距：30–50 kg
  尺寸：長度 >180 cm
  可否拆解：否
  ─────────────
  ⚠ 建議配置 2 人搬運（系統建議，實際依現場判斷）
```

**設計理由**：上半部是**觀察**（事實），下半部是**建議**（明確標註）。被問到依據時，回答為：「屬性由物品規格推導，人力建議為系統參考值，實際由班長判斷。」此回答站得住。

### 7.2 特殊處理標記

含冷媒設備（冰箱、冷氣）標記為「需特殊處理」。

> ⚠️ 冷媒回收的法規細節**未查證**。畫面文字建議寫中性的「含冷媒設備，需特殊處理」，不要寫具體法規要求。

## 八、Demo 設計

### 8.1 差異化定位 ✅

**主差異：系統「會算」，而非「知道得多」。**

| 候選 | 內容 | 天花板 |
|---|---|---|
| 知道規則 | 行李箱 3 只門檻 | **低** — 規則可塞進 prompt |
| **會算** ✅ | 插入成本、載重、改排 | **高** — ChatGPT 無你的案件池，算不出來 |

**選擇「會算」的理由**：本次主題為 Agent × 智慧城市，評審期待的是「系統在做決策」而非「AI 知道得多」。且此價值隨規模放大——28 件省 4 分鐘，300 件省整個班次，B2G 論述直接成立。

### 8.2 三分鐘腳本 ✅

| 時間 | 內容 |
|---|---|
| 0:00–0:30 | 儀表板已排好 28 件，班長的一天從這裡開始 |
| 0:30–1:00 | 現場拍攝會場物品送出（民眾端訊息流） |
| **1:00–2:00** | **決策軌跡逐行跑出，重點停在「超載 → 改查明日」** |
| 2:00–2:30 | 班長接受建議，路線更新 |
| 2:30–2:45 | （佐證）兩只行李箱 → 系統擋下，說明 3 只門檻 |
| 2:45–3:00 | 收尾：agent 決定做什麼，確定性程式負責算 |

**最後 30 秒必講**：明確說明「排程不經過 AI」。評審在 Agent 主題下反而會懷疑是否全丟給模型，主動說清楚可將質疑轉為加分。

**可選段落**（時間緊時砍）：裝潢廢料追問（15 秒），非主線但為良好鋪陳。

### 8.3 案件資料策略 ✅

**採用：預載 28 筆 fixture + 現場即時追加 1–2 筆**

現場新增的案件**真的**進入排程並觸發重算。

**預載資料須刻意設計，不得隨機生成**，至少包含：

| 用途 | 數量 | 演什麼 |
|---|---|---|
| 需特殊處理品項 | 2–3 | 屬性標記與特殊處理 |
| 位置偏遠 | 1–2 | 路線順序的明顯邏輯 |
| 造成超載 | 1 | 紅色警示 → 改排明日 |
| 資格有疑義 | 1 | needs_review 待審佇列 |

> **這批資料就是劇本。** 建議賽前設計完成，不要當天隨意編寫。

## 九、技術架構

沿用既有 hackathon-template：FastAPI + React(JSX) + uv。

```
backend/
├── models.py              前後端契約（第一小時定案）
├── services/              ★ 確定性層，不得 import ai
│   ├── eligibility.py     資格判定（三態）
│   ├── attributes.py      屬性標記與資源建議
│   ├── distance.py        距離矩陣（可替換來源）
│   └── scheduler.py       最近鄰居排序、插入成本、載重
├── ai/
│   ├── client.py          Gemini 唯一入口
│   ├── agent.py           ★ agent 迴圈與決策軌跡收集
│   ├── tools.py           function declarations
│   └── prompts/*.md
└── fixtures/
    ├── demo_cases.json    28 筆預載案件（劇本）
    └── distance_matrix.json
```

### 9.1 Gemini API 重要變更 ⚠️

**Interactions API 已 GA，`generateContent` 已標為 legacy。**
模板現有的 `ai/client.py` 使用舊寫法，**必須改寫**。

新寫法要點：
- `client.interactions.create(model=..., input=..., tools=[...])`
- 工具宣告為 JSON schema：`{"type": "function", "name":..., "description":..., "parameters": {...}}`
- 回應取 `interaction.steps`，過濾 `step.type == "function_call"`，取 `.name` / `.arguments` / `.id`
- 結果回傳：`input=[{"type": "function_result", "name":..., "call_id":..., "result": [{"type":"text","text":...}]}]` 搭配 `previous_interaction_id`
- 內建工具可混用：`tools=[{"type": "google_search"}, your_function]`
- `tool_choice` 置於 `generation_config`
- 官方範例模型字串為 `gemini-3.6-flash`，**須自行確認可用模型與 API key 權限**

### 9.2 Agent 工具定義

| 工具 | 實作位置 | 回傳 |
|---|---|---|
| `classify_item` | `ai/`（Gemini 視覺） | 物品類型、尺寸、材質、信心 |
| `check_eligibility` | `services/` | eligible / ineligible / needs_review + 依據 |
| `get_attributes` | `services/` | 重量級距、可否拆解、特殊處理標記 |
| `compute_insertion` | `services/` | 最佳插入位置、增加時間 |
| `check_capacity` | `services/` | 當前載重率、是否超載 |
| `query_next_day` | `services/` | 明日班次餘裕 |

**`check_capacity` 回傳超載 → agent 自行決定呼叫 `query_next_day`**，此即決策軌跡的關鍵一步。

### 10.2 風險與對策

| 風險 | 對策 |
|---|---|
| 單人開發、雙端 UI | 民眾端限 1.5 小時，逾時即凍結；兩端共用區塊渲染邏輯 |

| 範圍蔓延 | 明確不做：狀態查詢、案件取消、歷史記錄、互動地圖、多車分派 |
