# 開發流程演練規格書

> **這不是要你做一個產品，是要你量測自己的速度。**
>
> 目標是在真正比賽前，用一個假題目把整條流程跑一遍，
> 找出會卡住的地方，並校準「我以為要多久」和「實際要多久」的落差。
>
> 建議耗時：**4 小時**（真實比賽有效工時約 14–16 小時，這裡壓縮成 1/4 規模）

---

## 演練規則

1. **計時。** 每個階段開始與結束都記錄實際時間，填在最後的檢討表。
2. **不准查以前的專案。** 比賽當天你不會有現成程式碼可抄。
3. **超時就進下一階段。** 不要為了做完而拖延——演練的價值在暴露問題，不在完成度。
4. **中途會有一次強制干擾**（見階段四），照做。

---

## 模擬題目

> **訂閱服務盤點器**
>
> 使用者貼上信用卡帳單文字（或上傳截圖），系統辨識出所有訂閱服務，
> 計算年度總支出，找出功能重疊的訂閱，並給出可省下多少的建議。

選這題的原因：它的結構和大多數黑客松題目同構——

| 演練元素 | 對應真實比賽的能力 |
|---|---|
| 帳單文字／截圖 → 結構化項目 | AI 多模態抽取 |
| 年度費用計算 | 確定性運算 |
| 重疊訂閱偵測 | 互斥／組合邏輯 |
| 「取消 A 可省 X 元」 | 缺口提醒 |
| 白話總結 | AI 生成 |

**注意：題目本身不重要。** 你在練的是流程，不是這個產品。

**這份文件是演練專用。** 正式比賽時規格內容要換成真題目，
但「五階段拆解」這個流程結構可以直接沿用。

---

## 階段一：介面契約（目標 20 分鐘）

**只改 `backend/models.py`，不寫任何邏輯。**

需要定義的模型：

```
Subscription          抽取出的單筆訂閱
├── name              服務名稱
├── category          類別（影音／音樂／雲端／生產力／其他）
├── monthly_cost      月費
├── currency          幣別
└── confidence        辨識信心

SubscriptionAnalysis  單筆分析結果
├── subscription      原始項目
├── annual_cost       年度費用
├── status            keep / review / redundant
├── reasons           判定依據（list）
└── suggestion        建議（可為 null）

AuditRequest
├── text              帳單文字
├── image_base64      帳單截圖
└── options

AuditResponse
├── analyses          分析結果清單
├── total_annual      年度總支出
├── potential_saving  可節省金額
├── summary           AI 白話總結
└── used_fixture
```

**驗收條件**

- [ ] `uv run python -c "import models"` 沒有錯誤
- [ ] `docs/api.md` 已同步更新
- [ ] 能說出：如果有前端隊友，他現在能不能開始做？

**這一階段的意義**：真實比賽中，這 20 分鐘決定了團隊接下來能不能並行。

---

## 階段二：規則引擎（目標 50 分鐘）

**只改 `backend/services/`，完全不碰 AI。**

要實作的判定邏輯：

| 規則 | 內容 |
|---|---|
| 年度費用 | `monthly_cost × 12` |
| 重疊偵測 | 同一 category 有兩筆以上 → 較貴者標 `redundant` |
| 低使用疑慮 | 月費 < 100 且 confidence < 0.7 → 標 `review` |
| 節省計算 | 所有 `redundant` 項目的年度費用加總 |
| 建議文字 | `redundant` 項目給出「取消可省 X 元／年」 |

**同時寫測試。** 至少四個案例：

- [ ] 無重疊 → 全部 `keep`，`potential_saving` 為 0
- [ ] 同類別兩筆 → 較貴者為 `redundant`
- [ ] 同類別三筆 → 只保留最便宜的
- [ ] 低信心低價 → 標 `review`

**驗收條件**

- [ ] `uv run pytest` 全綠
- [ ] `services/` 裡沒有任何 `import` 指向 `ai/`

**這一階段的意義**：這是你回答「這不就是包一層 ChatGPT」的實體證據。跑得出測試，論述就成立。

---

## 階段三：AI 層與串接（目標 60 分鐘）

改 `ai/prompts/*.md`、`ai/tasks/*.py`、`main.py`。

**3-1 先做 fixture（15 分鐘）**

先寫 `fixtures/demo_items.json`，**在還沒接 API 之前**就讓 `DEMO_MODE=true` 能跑完整條流程。

準備三組：
- A：五筆訂閱、無重疊
- B：七筆、有兩組重疊 ← 主要 Demo 素材
- C：含低信心項目

**3-2 再接真實 API（45 分鐘）**

- 改 `prompts/extract.md`：帳單文字 → 訂閱清單
- 改 `prompts/explain.md`：分析結果 → 白話總結
- 確認 structured output 真的回傳合法 JSON

**驗收條件**

- [ ] `DEMO_MODE=true` 能完整跑完，不需網路
- [ ] `DEMO_MODE=false` 用真實帳單文字能跑通
- [ ] 用圖片輸入跑通一次
- [ ] 故意傳一段亂七八糟的文字，確認不會整個 crash

**這一階段的意義**：先做 fixture 再接 API，是本模板最重要的紀律。順序反過來的話，API 一出問題你就完全動不了。

---

## 階段四：前端與強制干擾（目標 50 分鐘）

改 `App.jsx`、`ResultCard.jsx`。

要呈現的東西：

- 年度總支出（大字）
- 可節省金額（強調色）
- 訂閱清單，依 `status` 用不同顏色標示
- `redundant` 項目顯示建議文字

**⚠️ 強制干擾演練**

**做到一半時（大約第 25 分鐘），把 Wi-Fi 關掉。**

然後在斷網狀態下，讓整條流程仍然跑得完。

- [ ] 幾秒內反應過來要切 `DEMO_MODE`？
- [ ] 切換後真的跑得動嗎？
- [ ] 前端有沒有因為 API 失敗而白畫面？

**這一階段的意義**：這是最貼近真實災難的一段。現場網路不穩、API 額度爆掉、Gemini 回應變慢——三件事都會發生，而你只有幾分鐘反應時間。

---

## 階段五：Demo 與收尾（目標 40 分鐘）

**5-1 填 `docs/demo-script.md`（15 分鐘）**

用 B 組 fixture 當主線，寫出逐步腳本。

**5-2 錄影（10 分鐘）**

錄一段完整成功操作，存本機。**這一步不准跳過**——真實比賽時你會很想跳過，先在演練時養成習慣。

**5-3 實際排練兩次（15 分鐘）**

計時。目標三分鐘內講完。

**驗收條件**

- [ ] 錄影檔存在本機（不是雲端）
- [ ] 排練過兩次，秒數記錄下來
- [ ] 能用一句話說出這個系統在解決什麼

### 校準公式

```
真實比賽的可用工時 ≈ 14 小時
你的實際倍率 = 實際總時數 ÷ 3.7 小時
真實比賽能做的規模 ≈ 14 ÷ 倍率 ÷ 3.7 倍的本次規模
```

倍率大於 1.5，代表**比賽當天必須砍掉三分之一的功能構想**。這個數字比任何精神喊話都有用。

## 常見的演練結果（對照參考）

| 現象 | 代表什麼 | 該怎麼辦 |
|---|---|---|
| 階段一超時 | 需求還沒想清楚就開工 | 當天前 90 分鐘的定案流程要更嚴格 |
| 階段二超時 | 判定邏輯設計不熟 | 當天要把規則簡化到只剩兩三條 |
| 階段三超時 | 卡在 SDK／structured output | **賽前務必先把 SDK 跑通一次** |
| 階段四斷網後手忙腳亂 | `DEMO_MODE` 沒真的驗證過 | 每次改完都順手測一次 |
| 階段五被跳過 | 你會在真實比賽跳過同樣的步驟 | 把錄影排進時程，當作硬性 checkpoint |
